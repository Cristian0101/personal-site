## Current launch state

All five titles are in preparation: Master Interviews, SDR/BDR Job Mastery, Break Up Your TAM, The Science of a Cold Call, and The Science of a Cold Email. Each has a proposed $39 USD one-time price. `purchaseEnabled`, `finalPdfApproved`, and `price.approved` in `src/lib/playbooks.ts` are false independently for each product. No payment or signup CTA is displayed. The existing Beehiiv integration is a general newsletter, not a verified launch-interest list, so these pages do not enroll visitors. The five attached approved mockups were converted to WebP at quality 94 without resizing, cropping, recoloring, or regeneration. Cyan (`#1be2f6`) and lime (`#badd49`) accents were sampled from the supplied artwork and are used only in the existing availability indicator. No finished PDFs or interior excerpts were supplied. ## Architecture

- `src/lib/playbooks.ts` owns public product content, amount in minor units, currency, approvals, cover, accent, modules, author, previews, SEO, and environment-variable names for the Stripe price and private file. All five titles use the same listing, page, image treatment, author section, preview gallery, CTA, and checkout implementation. The Premium Playbooks grid lists all five in collection order; each detail page uses the unchanged shared template.
- Stripe hosted Checkout is created server-side. The configured Stripe Price must be active, one-time, in the right mode, and match the displayed amount/currency. The private PDF must pass a storage HEAD check before creating checkout. The server records an immutable order snapshot before returning the checkout URL.
- Only a signature-verified webhook fulfills purchases. It retrieves the current Stripe Session, checks payment status, total, currency, mode, application metadata, and the exact price/quantity against the stored order. A redirect or success-page visit cannot issue access or record a conversion.
- PostgreSQL primary keys enforce one purchase and one verified-purchase event per Session, including concurrent webhook deliveries. A purchase is committed before email. Email uses a deterministic Resend idempotency key; failures return HTTP 500 so Stripe retries. Initial access links expire seven days after purchase. Recovery sends new 24-hour links. Resend deduplicates keys for 24 hours; a retry after that window can send another access email but cannot create another purchase/conversion. Very late retries can contain an expired initial link; the email includes the recovery URL.
- The paid PDF stays in private S3-compatible storage and streams through an authenticated POST. Tokens are HMAC-signed; emailed links put the token in the URL fragment so it is not sent to the server or as a referrer. The access page removes it from browser history and sends it in an Authorization header. Payment is checked again at download, including refunds and disputes. Refund/dispute webhooks revoke access. Turning off new purchases does not disable existing customers' access.
- Recovery is rate limited per trusted IP and hashed email, sends only to the original purchaser, and returns the same success copy for matches and non-matches. Rate limits are durable atomic PostgreSQL counters. The default trusted header is Vercel's overwritten `x-vercel-forwarded-for`; on another host adapt `requestIp` to an overwritten proxy header. Without it, requests intentionally share a conservative global bucket.
- No analytics integration existed. Anonymous `product_view`, server-created `checkout_started`, and webhook-only `purchase_verified` events are stored in `commerce_events`. Test/live are separated by `livemode`; filter it in reports. Views are best effort and will be absent until a DB is configured. Client events cannot claim a conversion. No emails/IPs are included in funnel events.

## Configure a sandbox

1. Copy `.env.commerce.example` values into your local `.env.local` or deployment secret manager. Keep `COMMERCE_MODE=test`. Use a Stripe sandbox `sk_test_` key and a matching one-time $39 USD Price (or update the product config and Stripe Price together).
   Each title has its own Stripe Price and file key: `MASTER_INTERVIEWS_STRIPE_PRICE_ID` / `MASTER_INTERVIEWS_FILE_KEY`, `SCIENCE_COLD_CALL_STRIPE_PRICE_ID` / `SCIENCE_COLD_CALL_FILE_KEY`, and `SCIENCE_COLD_EMAIL_STRIPE_PRICE_ID` / `SCIENCE_COLD_EMAIL_FILE_KEY`. The two new editions use `SDR_BDR_JOB_MASTERY_STRIPE_PRICE_ID` / `SDR_BDR_JOB_MASTERY_FILE_KEY` and `BREAK_UP_YOUR_TAM_STRIPE_PRICE_ID` / `BREAK_UP_YOUR_TAM_FILE_KEY`. One title's readiness does not enable another.
2. Provision a private PostgreSQL database and run `db/commerce.sql`. Use its SSL connection URL in `COMMERCE_DATABASE_URL`. Restrict credentials to the commerce tables and back up the database. Separate test and production databases.
3. Upload each **approved final** PDF to a private bucket; set its Content-Type to `application/pdf`. Set the corresponding product file-key variable to its object key. Keep Block Public Access enabled. Give runtime IAM only `s3:GetObject` on approved book keys (HEAD uses GetObject permission). Do not place paid files under `public/`, `content/`, Git, or a public URL. Verify an unauthenticated object request is denied. Optional `COMMERCE_S3_ENDPOINT` supports services such as R2 and requires HTTPS.
4. Configure a verified sending domain/address in Resend and put its API key and From address in the environment. Send a sandbox message to an address you control and verify delivery. The application does not reuse Beehiiv for transactional purchase emails.
5. Set a random access secret with at least 32 characters. Set `COMMERCE_SITE_URL` to the exact local or public origin, without a path. Outside localhost it must use HTTPS. Do not rotate the signing secret without planning for existing links; recovery issues links with the current secret.
6. Forward sandbox webhooks: `stripe listen --forward-to http://127.0.0.1:3218/api/commerce/webhook`. Use its signing secret. Subscribe to `checkout.session.completed`, `checkout.session.async_payment_succeeded`, `checkout.session.async_payment_failed`, `checkout.session.expired`, `charge.refunded`, and `charge.dispute.created` on the deployed endpoint. Use Stripe snapshot events. The SDK pins its supported API version; configure the endpoint consistently.
7. Once the final PDF and price are approved, update `status` to `published`, `purchaseEnabled`, `finalPdfApproved`, and `price.approved` to true in the product data. Update SEO and delivery copy to describe the finished edition. Set `COMMERCE_VERIFIED=true` only after configuration has been independently verified. All gates must pass before checkout is exposed. Keep the committed product disabled until this work is complete.

## Acceptance before live purchases

Use Stripe test card `4242 4242 4242 4242`, a future expiry, and any valid CVC in the sandbox. Verify the complete hosted flow, receipt, signature-verified webhook, one DB purchase, one conversion, email arrival, and actual PDF download. Re-send the same webhook and deliver it concurrently; verify no additional purchase or conversion. Test a declined card, cancelled and expired sessions, delayed success/failure, unavailable email followed by webhook retry, email recovery, expired/tampered links, no authorization, refunds, and disputes. A success-page visit without a verified paid order must issue no access. Confirm the display amount matches Stripe. Configure tax/refund/support policies appropriate to the business before enabling live purchases.

To go live, use live Stripe keys/Price/webhook secret, a production database, private final PDF, verified sender, HTTPS origin, and a production signing secret. Set `COMMERCE_MODE=live`, `COMMERCE_VERIFIED=true`, and **only after the live setup is verified** `COMMERCE_LIVE_VERIFIED=true`. Live mode requires `sk_live_`; test keys cannot accidentally accept live payments. Do not set these flags merely because the page renders. None of these services or credentials have been provisioned by this implementation.

## Operations and verification

Monitor failed webhook deliveries and replay them from Stripe after resolving outages. A successful webhook acknowledges durable purchase processing and email acceptance; monitor Resend bounces separately. Keep the recovery route available after sales close. Purge `commerce_rate_limits` rows older than a day on a scheduled database maintenance job; retain purchases for recovery according to your retention policy. Protect infrastructure logs and do not log tokens or customer emails.

`npm run test:commerce` checks independent product configuration, offline payment, cross-product isolation, signature, idempotency/retry, and token invariants. It uses mocked persistence/email and does not prove a deployed database, real payment, or real email delivery. `TEST_ORIGIN=http://127.0.0.1:3218 npm run test:playbooks` checks all five products at 390/768/1440px in light/dark themes, long titles, navigation, appearance controls, hidden previews, disabled checkout, metadata, product-view event identity, collection order and all five free download endpoints. Also run the existing resource tests, lint, TypeScript, and production build. If browsers are missing, use `npx playwright install chromium`.

The framework was updated from Next.js 16.1.6 to 16.4.6 to resolve existing production dependency advisories. Repository-wide lint still reports existing hook/ref issues in Appearance, BuildingBoard, Header, IntoDeck, and PageTransition. New playbook and commerce source is linted separately; those unrelated components have not been refactored.

Approved interior previews go in `previews` with intrinsic dimensions, descriptive alt text, and captions. The gallery renders only for 2–4 assets and uses a native modal dialog for focus trapping, Escape, and return focus. It is hidden in the current launch state.
